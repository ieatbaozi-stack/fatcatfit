# วิจัยเตรียม R1: Better Auth, Google บน iOS PWA, ส่งอีเมล OTP, PDPA, CSP nonce

วันที่เปิดดูทุกแหล่ง: **2026-11-18** · ผู้เขียน: researcher · ต่อยอดจาก [2026-11-15-auth.md](2026-11-15-auth.md) (ไม่ทำซ้ำสิ่งที่ยืนยันแล้ว)
ระดับความมั่นใจ: **[ทางการ]** เอกสารเจ้าของเรื่อง · **[โค้ด]** อ่านจาก better-auth 1.7.25 ที่ติดตั้งใน `node_modules` (ตรงกับรุ่นที่ใช้) · **[รอง]** แหล่งรอง · **[อนุมาน]** ข้อสรุปของผู้เขียนจากข้อเท็จจริง ไม่ใช่ข้อความในเอกสาร · **[ไม่ได้]** ยืนยันไม่ได้

## คำตอบสั้น
1. Better Auth: ตั้งได้ครบ · hook โค้ดเชิญใช้ `databaseHooks.user.create.before` ได้ (รับ `ctx` ที่เป็น `null` ได้) · `deleteUser` ลบ session + account + user แต่ **ไม่ลบ `verification`** · ปลั๊กอิน OTP มี rate limit ของตัวเองอยู่แล้ว **3 ครั้ง/60 วิ ต่อเส้นทาง** (ไม่มีในเอกสาร พบในโค้ด)
2. Google ใน iOS standalone: Apple ยืนยันว่า Home Screen web app แยก cookie จาก Safari และลิงก์นอก scope เปิดใน Safari View Controller → redirect flow มีความเสี่ยงสูง ไม่มีเอกสารบอกว่าใช้ได้ ต้องทดสอบเครื่องจริง · โหมด Testing: 100 ผู้ใช้ทดสอบ แต่ถ้าขอแค่ openid/email/profile ไม่หมดอายุ 7 วัน ไม่ต้อง verify
3. อีเมล: Gmail SMTP ใช้ได้ต่อ (ฟรี ไม่ต้องมีโดเมน) · Resend ฟรีต้องมีโดเมนของตัวเองจึงส่งถึงคนอื่นได้ ใช้ไม่ได้กับ `*.vercel.app` → แนะนำ Gmail SMTP ต่อไป
4. PDPA: ข้อมูลสุขภาพต้องมีความยินยอมโดยชัดแจ้ง (ม.26 + ม.19) · ข้อยกเว้นกิจกรรมส่วนตัว (ม.4(1)) **ไม่ชัดว่าครอบคลุมแอปนี้** อย่าพึ่งพา
5. CSP nonce: เอกสาร Next ระบุว่าทุกหน้าต้อง dynamic (แอปเราเป็นอยู่แล้ว) ราคาที่ต้องจ่ายจริงคือ HTML ที่ service worker แคชไว้ออฟไลน์

## 5. CSP nonce กับ Next.js 16

| ข้อเท็จจริง | แหล่ง | ระดับ |
|---|---|---|
| Next 16 เปลี่ยนชื่อ middleware เป็น **`proxy.ts`** (v16.0.0) · ใช้ Node.js runtime โดยปริยาย · ตั้ง nonce + CSP ใน proxy แล้วส่ง `x-nonce` เป็น request header | [proxy](https://nextjs.org/docs/app/api-reference/file-conventions/proxy) · [CSP guide](https://nextjs.org/docs/app/guides/content-security-policy) (lastUpdated 2026-03-20) | ทางการ |
| ใช้ nonce → **ทุกหน้าต้อง render แบบ dynamic**: ปิด static optimization และ ISR · CDN แคชหน้าไม่ได้ (ถ้าไม่ตั้งเพิ่ม) · **PPR ใช้ร่วมไม่ได้** · ช้าลงและกินเซิร์ฟเวอร์มากขึ้น | CSP guide | ทางการ |
| Next เติม nonce ให้อัตโนมัติกับ framework script, bundle ของหน้า, inline script/style ที่ Next สร้าง · อ่านใน Server Component ผ่าน `headers().get("x-nonce")` | CSP guide | ทางการ |
| ทางเลือกไม่ใช้ nonce: ตั้ง CSP ใน `next.config` ด้วย `'unsafe-inline'` (ที่ repo ใช้อยู่) · หรือ SRI `experimental.sri` (ทดลอง, App Router, คงความ static ได้, `script-src 'self'` ไม่มี unsafe-inline) | CSP guide | ทางการ |
| ใน dev ต้องมี `'unsafe-eval'` · production ไม่ต้อง | CSP guide | ทางการ |
| ปัจจุบัน repo: `next.config.ts` ใช้ `'unsafe-inline'` ทั้ง script และ style · `form-action 'self'` · ทุกหน้า dynamic (ƒ) จาก next-intl cookie | `next.config.ts` บรรทัด 12–35 | อ่านจากไฟล์ |

**ข้อดี nonce:** ตัด `'unsafe-inline'` ออกจาก script (+ style) → XSS ที่ฉีด inline script ถูกบล็อก · เหมาะกับแอปข้อมูลสุขภาพ · ค่าเสียเรื่อง static/CDN/PPR เป็นศูนย์สำหรับเราเพราะหน้า dynamic อยู่แล้ว **[อนุมาน]**

**ข้อเสีย/ความเสี่ยงที่ต้องตัดสิน:**
- service worker (ADR 0005) แคช HTML ไว้ใช้ออฟไลน์: HTML ที่แคชมี nonce ของตอนนั้นฝังอยู่ ขณะที่ CSP header มากับ response เดิม ถ้า SW คืน Response ที่แคชทั้งก้อน (รวม header) nonce กับ header ยังตรงกัน แต่ถ้า SW สร้าง response ใหม่โดยไม่ใส่ header หรือเอา HTML ไปผสม จะพัง → ต้องมีเทสต์ออฟไลน์บน iOS **[อนุมาน — ไม่มีเอกสารพูดถึงคู่นี้]**
- ต้องเขียน `proxy.ts` ที่รันทุก request (ยกเว้น static/prefetch) → เพิ่มงาน/ความหน่วงเล็กน้อย; ต้องมีเทสต์ว่า header มาจริงทุกหน้ารวม error page
- style nonce: `style-src 'nonce-…'` อาจพังกับ inline style ของไลบรารี (Tailwind ปกติเป็นไฟล์ CSS ไม่ใช่ปัญหา) — ลดความเสี่ยงโดยคง `'unsafe-inline'` ไว้เฉพาะ style ก็ได้ **[อนุมาน]**
- `form-action 'self'` อาจบล็อก redirect ไป accounts.google.com ถ้าล็อกอิน Google ทำผ่าน form POST (บางเบราว์เซอร์นับ redirect หลัง form) · Better Auth `signIn.social` ปกติใช้ fetch แล้วเปลี่ยนหน้าด้วย JS ซึ่งไม่โดน · ต้องทดสอบ **[อนุมาน]**
- เอกสารคือ CSP guide ฉบับ 2026-03-20 (หลัง Next 16 ออก) แต่ยังไม่ได้ทดสอบกับ 16.4.6 ที่ติดตั้ง

## ผลต่อโปรเจกต์ (สิ่งที่ PRD/ADR ต้องปรับ)
- **ADR 0002 ข้อ 3**: ตัวเลข rate limit ต้องเขียนกำกับว่า OTP มีค่าเริ่ม 3/60 วิ ในตัวและ `emailOTP.rateLimit` ตั้งได้ค่าเดียวทั้งปลั๊กอิน (ถ้าต้องแยกตามเส้นทาง ใช้ `rateLimit.customRules` ของ Better Auth) · ปิดข้อค้าง "header IP บน Vercel": `x-forwarded-for` ปลอดภัยบน Vercel ตามเอกสาร
- **ADR 0002 ข้อ 2**: เพิ่มจุดกั้นที่ send-OTP (ดูข้อสังเกตหัวข้อ 1) · เทสต์ว่า `ctx` เป็น null ได้ · ยืนยัน `getCookie` ใน database hook ตั้งแต่ต้นรอบ
- **ADR 0002 ข้อ 7 (ลบบัญชี)**: ต้องลบ `verification` เอง (Better Auth ไม่ลบ) และอย่าพึ่ง `/delete-user` ของ Better Auth เพราะเช็ก session สด 1 วัน (endpoint `DELETE /api/me` ของเราถูกทางแล้ว) · ตรวจว่า FK cascade ลบตารางของเราครบ
- **ADR 0002 ข้อ 4**: ใส่ host/port Gmail SMTP แล้ว (smtp.gmail.com 465/587) และบันทึกว่าเอกสาร Google ขัดกันเรื่อง 500 กับ 2,000/วัน และเรื่อง app password กับ OAuth
- **ข้อ 5 (iOS)**: Apple ยืนยันว่า cookie แยก → ให้ถือว่า redirect มาตรฐาน**น่าจะไม่ผ่าน**บนแอปติดตั้ง และแผนทางถอย (OTP อย่างเดียวบน iPhone ที่ติดตั้ง) ควรเป็นกรณีฐานในการประเมินงาน
- **PRD ข้อ 8 / ความเสี่ยง PDPA**: บันทึกว่าไม่พึ่ง ม.4(1) · notice ต้องมีครบรายการ ม.23 (รวมระยะเวลาเก็บ ผู้รับข้อมูล = Vercel/Neon/Google, ส่งไปนอกประเทศ, ช่องทางติดต่อผู้ควบคุม) · ปุ่ม consent แยกจากข้อความอื่น ไม่ผูกกับเงื่อนไขอื่น · ถอนได้ง่ายเท่าให้ (ADR: ถอน = ลบบัญชี ควรบอกผลชัดตาม ม.19) · มีแผนแจ้งเหตุละเมิด 72 ชม.
- **CSP**: ต้องให้ ops/security ตัดสินและ ADR 0005 ต้องระบุผลต่อ HTML ที่ SW แคช

## ยังไม่รู้
- Google redirect/ID-token ใน iOS standalone รุ่นปัจจุบันทำงานอย่างไรจริง (ต้อง iPhone จริง) · Safari View Controller ใช้ cookie jar ร่วมกับแอปหรือ Safari หรือแยก ไม่มีเอกสารยืนยัน

- ตัวบท PDPA จากราชกิจจาฯ ฉบับจริงและแนวปฏิบัติ สคส. เรื่องหลักฐานความยินยอม · ม.4(1) ใช้กับแอปนี้ได้หรือไม่ (ต้องผู้รู้กฎหมาย)

### ตัวเลขที่ควรเขียนในประกาศ
- **ฐานข้อมูล (Neon):** "เมื่อคุณลบบัญชี ข้อมูลถูกลบจากฐานข้อมูลทันที แต่ผู้ให้บริการฐานข้อมูลอาจกู้คืนข้อมูลย้อนหลังได้ไม่เกิน 6 ชั่วโมง" (ตัวเลขจากเอกสาร Free) · ถ้าจะครอบคลุมกรณีลบทั้งโปรเจกต์ใช้ "ไม่เกิน 7 วัน" · อย่าเขียนว่า "ลบถาวรทันที" และอย่าเขียนว่ามี backup ไม่มี เพราะ backup ภายในของ Neon ยืนยันไม่ได้
- **Log ของ Vercel:** "บันทึกคำขอของระบบโฮสติ้ง (path, user agent, ค่าที่ต่อท้าย URL, IP) เก็บในหน้าจัดการ **ไม่เกิน 1 ชั่วโมง**" · ส่วนที่ Vercel เก็บเองตามนโยบายของตน ไม่มีตัวเลข ให้เขียนว่า "ตามนโยบายของ Vercel" แทนตัวเลข · ข้อควรระวังเชิงโค้ด: อย่า `console.log` อีเมล/OTP/ข้อมูลสุขภาพ เพราะจะอยู่ใน log
- **อีเมล Gmail:** "สำเนาอีเมลที่ระบบส่ง (มีที่อยู่อีเมลของคุณและรหัส OTP) อาจอยู่ในกล่องส่งแล้วของบัญชีแอปจนกว่าผู้ดูแลลบ" · ถ้า boss ตกลงจะลบเป็นรอบ ให้เขียน "ลบทุก X วัน" ตามที่ทำจริงได้ + ถังขยะอีก 30 วัน (ถ้าไม่ลบถังขยะเอง) · ห้ามสัญญาตัวเลขที่ไม่มีใครทำ

### ประเทศ (สำหรับม.28 ในประกาศ)
- ฐานข้อมูล: **สิงคโปร์** (Neon, AWS `ap-southeast-1`) [ทางการ] · ฟังก์ชัน Vercel: **สิงคโปร์** (sin1) ตามที่ตั้งค่า [ทางการว่า region ที่เลือกคือที่รัน] — ที่ตั้งจริงของ log/ระบบ Vercel: **สหรัฐอเมริกาและประเทศอื่น** (ตามนโยบายของ Vercel) [ยืนยันประเทศเฉพาะไม่ได้]
- Google (ล็อกอิน + Gmail): **หลายประเทศทั่วโลก ระบุไม่ได้** [ทางการ]
- ถ้อยคำที่ปลอดภัย: "สิงคโปร์ สหรัฐอเมริกา และประเทศอื่นที่ผู้ให้บริการดำเนินงาน" [อนุมาน — ตัวบท ม.28 ให้ผู้รู้กฎหมายตรวจ]

### ข้อ 4: คำแนะนำ
1. **ถือว่าเก็บ:** เอกสารบอกว่าสำเนาลง Sent อัตโนมัติ และไม่มีสวิตช์ฝั่งบัญชี จึงต้องเขียนในประกาศว่า Gmail ของแอปเก็บอีเมลผู้ใช้และ OTP ไว้
2. **ลดความเสี่ยง:** OTP หมดอายุใน 5 นาทีตามค่าเริ่ม (`expiresIn` 300) และใช้ครั้งเดียว ค่าเสี่ยงจากสำเนาจึงต่ำ *(หมายเหตุ secretary 2026-11-19: โค้ดตั้ง `expiresIn: 600` (10 นาที) ตาม R1 contract เกณฑ์ 4 ใน `src/lib/auth/create-auth.ts` — ไม่ใช่ 300 ที่ข้อนี้อ้างถึง ข้ออื่นของข้อ 4 ยังใช้ได้)* · ใช้บัญชี Gmail เฉพาะแอป เปิด 2-Step · ให้ boss ลบกล่อง "ส่งแล้ว" เป็นระยะ (เขียนเป็นขั้นตอนใน runbook ไม่ใช่โค้ด) · ลบถังขยะด้วยถ้าต้องการให้หายทันที
3. **ทางออกถาวร:** ย้ายไปบริการส่งเมลแบบ API ที่ไม่เก็บกล่องส่ง (เช่น Resend) ต้องมีโดเมน → ตามข้อสรุปข้อ 3 เดิมของรายงานนี้ ยังอยู่ที่ Gmail ไปก่อน · การตั้งค่า "ไม่เก็บสำเนา" ในโค้ด/nodemailer ยืนยันไม่ได้ (ไม่ได้ตรวจเอกสาร nodemailer) อย่าสัญญาในประกาศ
4. ถ้าต้องการให้ตัวเลขในประกาศเป็นจริงเสมอ: ใช้ถ้อยคำ "จนกว่าผู้ดูแลลบ" แทน "ไม่เกิน X วัน"

### ผลต่อโปรเจกต์
- ประกาศความเป็นส่วนตัวต้องมีหัวข้อ "ระยะเก็บ" ตาม ม.23(3) โดยใช้ตัวเลขข้างบน และ "ผู้รับข้อมูล/ไปต่างประเทศ" ตาม ม.28
- ADR 0002/runbook: เพิ่มงานลบกล่อง "ส่งแล้ว" ของ Gmail แอป · ข้อห้ามเขียน PII/OTP ลง console (เพราะเข้า runtime log) · ระบุว่าถ้า boss ต้องการ "ลบจริงทันที" ของ Neon ทำไม่ได้เกินกรอบ 6 ชม./7 วัน

### ยังไม่รู้ (ภาคผนวก)
- Neon: อายุ backup/สำเนาภายในหลัง history 6 ชม. และหลังลบโปรเจกต์ครบ 7 วัน · มีสำเนาข้ามภูมิภาคหรือไม่ (ไม่พบข้อความ) · อาจต้องเปิด [neon.com/privacy-policy] หรือ DPA (ไม่ได้เปิดรอบนี้)
- Vercel: ประเทศที่เก็บ log/metadata · ระยะเก็บ log ภายในนอกหน้า dashboard · IP ปรากฏเป็นฟิลด์ใน log หรือไม่ (เอกสารหน้า log ไม่ระบุ) · ไม่ได้เปิด DPA ของ Vercel
- Google: ประเทศเฉพาะที่ประมวลผลล็อกอิน/Gmail
- Gmail: ว่ามีวิธีฝั่งเซิร์ฟเวอร์ไม่ให้เก็บสำเนา SMTP หรือไม่ (เอกสารที่เปิดได้ไม่มี) · ว่า Gmail ส่วนตัวต่างจาก Workspace หรือไม่ (หน้านั้นไม่แยก)
