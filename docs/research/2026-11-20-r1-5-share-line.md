# วิจัย R1.5: เปิดลิงก์เชิญใน LINE, Google OAuth ใน WebView, Web Share, clipboard

วันที่เปิดดูทุกแหล่ง: **2026-11-20** · ผู้เขียน: researcher
ระดับความมั่นใจ: **[ทางการ]** เอกสารเจ้าของเรื่อง · **[อนุมาน]** ข้อสรุปของผู้เขียน · **[ไม่ได้]** ยืนยันไม่ได้

## คำตอบสั้น
1. Google **บล็อก** OAuth ใน embedded webview (Android WebView, iOS WKWebView) ด้วย `disallowed_useragent` · ทางออกที่ Google ระบุคือ Custom Tabs / SFSafariViewController / เบราว์เซอร์ปกติ · **ไม่มีเอกสารทางการ** ว่าเบราว์เซอร์ในแอป LINE เป็น WebView ชนิดไหน จึงสรุปไม่ได้ว่า Google login ใน LINE ใช้ได้หรือไม่ → ถือว่าเสี่ยง ต้องทดสอบเครื่องจริง
2. LINE มีวิธีทางการ: ต่อ `?openExternalBrowser=1` ที่ URL · เอกสาร **ไม่พูดถึง fragment** และไม่พูดถึงพฤติกรรม iOS → ไม่ทราบว่า `#invite=` รอดไหม
3. `navigator.share` ต้อง HTTPS + กดปุ่มโดยตรง · `clipboard.writeText` ต้องอยู่ใน click handler · ตัวเลขรุ่นของ share บน iOS/PWA ยืนยันได้บางส่วน (ดูตาราง)
4. เอกสารทางการของ LINE **ไม่พูด**เรื่อง storage/cookie แยกจาก Safari/Chrome · ที่ยืนยันได้คือ LIFF ถือเบราว์เซอร์ในแอปเป็น "external browser" ชนิดหนึ่ง

## 1. Google OAuth ใน WebView

| ข้อเท็จจริง | แหล่ง | ระดับ |
|---|---|---|
| Google บล็อกคำขอ OAuth จาก embedded webview ตั้งแต่ 2021-09-30 · ผู้ใช้เห็น error `disallowed_useragent` · ครอบคลุม Android WebView, iOS/macOS WKWebView (และ UIWebView เก่า) | [Google Developers Blog](https://developers.googleblog.com/en/upcoming-security-changes-to-googles-oauth-20-authorization-endpoint-in-embedded-webviews/) | ทางการ |
| ทางเลือกที่ Google แนะนำ: Android = เบราว์เซอร์หลัก/App Links/Custom Tabs · iOS = เบราว์เซอร์หลัก/Universal Links/SFSafariViewController | เดียวกัน | ทางการ |
| นโยบาย: ห้ามส่งคำขอ OAuth ไปยัง embedded user-agent ที่นักพัฒนาควบคุม (แทรกสคริปต์ อ่าน cookie ได้) · สภาพแวดล้อมที่ใช้ล็อกอินต้องให้ผู้ใช้ตรวจ URL และความปลอดภัยของการเชื่อมต่อได้ | [OAuth policies](https://developers.google.com/identity/protocols/oauth2/policies) | ทางการ |
| เบราว์เซอร์ในแอป LINE (iOS/Android) เป็น WebView ชนิดไหน (WKWebView หรือ SFSafariViewController / Android WebView หรือ Custom Tabs) | ค้นแล้วไม่พบเอกสาร LINE ระบุ | **[ไม่ได้]** |
| LINE Login docs หน้า browser-support เปิดไม่ได้ (HTTP 403) | [developers.line.biz/.../browser-support](https://developers.line.biz/en/docs/line-login/browser-support/) | **[ไม่ได้]** |

หมายเหตุ: Google ยอมรับ SFSafariViewController/Custom Tabs แต่ไม่ได้บอกว่าแอปของ LINE ใช้ตัวไหน จึงห้ามสรุปว่าใช้ได้หรือไม่ได้จากเอกสาร

## 2. เปิดลิงก์ LINE ในเบราว์เซอร์ภายนอก

| ข้อเท็จจริง | แหล่ง | ระดับ |
|---|---|---|
| `https://example.com/?openExternalBrowser=1` → LINE เปิด URL ในเบราว์เซอร์ภายนอก | [LINE URL scheme](https://developers.line.biz/en/docs/line-login/using-line-url-scheme/) (หัวข้อ opening a URL in an external browser) | ทางการ |
| `?openInAppBrowser=0` → เปิดใน Chrome custom tab · **เฉพาะ LINE บน Android** | เดียวกัน | ทางการ |
| ใช้กับ URL ที่เปิดจากแอป LINE · **ใช้ไม่ได้กับ LIFF URL** | เดียวกัน | ทางการ |
| fragment (`#...`) ถูกรักษาไว้หรือไม่ | หน้านั้นไม่พูดถึง | **[ไม่ได้]** |
| พฤติกรรมบน iOS ของ `openExternalBrowser` | หน้านั้นไม่พูดถึง (ระบุแพลตฟอร์มแค่ที่ openInAppBrowser) | **[ไม่ได้]** |
| เอกสารไม่ได้แยกว่า parameter ต้องอยู่ก่อน `#` หรือไม่ (ตามมาตรฐาน URL, query มาก่อน fragment เสมอ) | | **[อนุมาน]** รูปแบบที่ถูกคือ `https://host/path?openExternalBrowser=1#invite=...` ต้องทดสอบเครื่องจริงว่า `#invite` ถึง Safari/Chrome |

## 3. Web Share และ clipboard

| ข้อเท็จจริง | แหล่ง | ระดับ |
|---|---|---|
| `navigator.share()`: ต้อง secure context (HTTPS) · ต้องมี transient activation (เรียกจาก click) · ต้องมี `url`/`text`/`title`/`files` อย่างน้อยหนึ่ง · โยน `AbortError` เมื่อผู้ใช้ยกเลิก · `NotAllowedError` ถ้าไม่มี activation · MDN ระบุ "Limited availability" (ไม่ใช่ Baseline) | [MDN share](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/share) | ทางการของมาตรฐานเว็บ (MDN ไม่ใช่เจ้าของ API แต่เป็นอ้างอิงหลัก) |
| ข้อมูลรุ่น (MDN browser-compat-data) ของ `canShare`/share: Chrome Android 75 · Safari 14 · Safari iOS 14 · Chrome desktop: ก่อน 128 รองรับเฉพาะ ChromeOS และ Windows, 128+ รองรับทั่วไป · Edge 93 (ก่อนนั้น Windows เท่านั้น) | [BCD Navigator.json](https://raw.githubusercontent.com/mdn/browser-compat-data/main/api/Navigator.json) (อ่านได้เฉพาะครึ่งแรกของไฟล์ ข้อมูลมาจาก canShare ไม่ใช่ share โดยตรง) | จากแหล่งรอง/บางส่วน |
| `navigator.share` ใน PWA ที่ติดตั้งบน iOS (standalone) | ไม่พบเอกสารยืนยัน | **[ไม่ได้]** |
| `navigator.share` บน iOS Safari 16.4 โดยเฉพาะ | BCD ชี้ว่าเริ่มที่ 14 จึงครอบคลุม 16.4 แต่ไม่ได้ดูหน้า Apple โดยตรง | จากแหล่งรอง |
| `clipboard.writeText()`: Baseline widely available · ต้อง HTTPS · Chrome 66+ (ตั้งแต่ 107 ต้องเรียกใน user gesture หรือมี permission `clipboard-write`) · Safari/iOS 13.1+ ต้องเรียกใน user gesture handler · ปฏิเสธด้วย `NotAllowedError` | [MDN writeText](https://developer.mozilla.org/en-US/docs/Web/API/Clipboard/writeText) · [BCD Clipboard.json](https://raw.githubusercontent.com/mdn/browser-compat-data/main/api/Clipboard.json) | แหล่งรอง (MDN/BCD) |
| `clipboard.writeText` ในเบราว์เซอร์ในแอป LINE | ไม่พบเอกสาร | **[ไม่ได้]** |

## 4. Storage ของเบราว์เซอร์ใน LINE

| ข้อเท็จจริง | แหล่ง | ระดับ |
|---|---|---|
| LINE in-app browser = "เบราว์เซอร์เฉพาะภายในแอป LINE" · LIFF จัดเป็น external browser ชนิดหนึ่ง (`liff.getContext().type` = `external`) · แยกจาก LIFF browser | [LIFF differences](https://developers.line.biz/en/docs/liff/differences-between-liff-browser-and-line-in-app-browser/) · [LIFF tips](https://developers.line.biz/en/tips/2026/08/06/between-liff-browser-and-external-browser/) | ทางการ |
| localStorage/cookie ของเบราว์เซอร์ใน LINE แยกจาก Safari/Chrome หรือไม่ | ทั้งสองหน้าไม่พูดถึง | **[ไม่ได้]** |
| ในทางปฏิบัติ WebView ในแอปมักไม่แชร์ cookie jar กับเบราว์เซอร์หลัก (Apple ยืนยันแล้วว่า Home Screen web app แยกจาก Safari ตาม [2026-11-18-r1-auth.md](2026-11-18-r1-auth.md)) | | **[อนุมาน]** ไม่ใช่ข้อความจาก LINE |

## ผลต่อโปรเจกต์ (ข้อเสนอ ไม่ใช่การตัดสิน)
- **ข้อความแชร์:** ลิงก์ที่ใส่ในข้อความเชิญควรเป็น `https://<host>/?openExternalBrowser=1#invite=<code>` (query ก่อน fragment) · ต้องทดสอบเครื่องจริง iOS + Android ว่า (ก) LINE เปิด Safari/Chrome (ข) `#invite` ยังอยู่ · ถ้า fragment หาย ต้องมีทางสำรอง: ให้ผู้ใช้วางโค้ดเองในหน้าสมัคร
- **ตรวจ in-app browser ฝั่ง frontend:** ตรวจ user agent มีคำว่า `Line/` แล้วแสดงแผ่นแนะนำ "เปิดในเบราว์เซอร์" (ปุ่มคัดลอกลิงก์ + ขั้นตอนเมนู ⋯ ของ LINE) ก่อนให้กดปุ่ม Google · ไม่พบเอกสารทางการเรื่องรูปแบบ UA ของ LINE ต้องยืนยันเอง **[ไม่ได้]**
- **ปุ่มแชร์:** ใช้ `navigator.share` เมื่อมี (feature-detect `navigator.share`) เรียกจาก click เท่านั้น จับ `AbortError` ไม่ถือเป็นข้อผิดพลาด · สำรองด้วย `clipboard.writeText` ใน click handler · สำรองสุดท้าย: แสดงลิงก์ให้เลือกคัดลอกเอง (เพราะ clipboard ใน LINE ไม่ได้ยืนยัน)
- **จอยินดีต้อนรับ:** ถ้าผู้ใช้สมัครใน LINE แล้วต้องเปิดต่อใน Safari/Chrome ให้สมมติว่า session ไม่ตามไป · จอควรบอกให้ล็อกอินอีกครั้งด้วยวิธีเดิม (Google/OTP) ที่เบราว์เซอร์หลัก และบอกให้ "เพิ่มลงหน้าจอหลัก" จากเบราว์เซอร์หลัก ไม่ใช่จาก LINE
- **PRD/ADR:** ADR ของ auth ควรเพิ่มว่าเส้นทางหลักสำหรับคนเข้าจาก LINE คืออีเมล OTP (ไม่ขึ้นกับ Google) หรือเปิดนอก LINE ก่อน Google · รายการทดสอบเครื่องจริงของ boss เพิ่ม 3 ข้อ: UA ของ LINE, fragment รอดหลัง openExternalBrowser, Google login ใน LINE

## สิ่งที่ยังไม่รู้
- ชนิด WebView ของ LINE บน iOS/Android และผลจริงของ Google OAuth ในนั้น
- `openExternalBrowser=1` รักษา `#fragment` ไหม และทำงานบน iOS อย่างไร
- localStorage/cookie ของเบราว์เซอร์ LINE แยกจากเบราว์เซอร์หลักหรือไม่ (เอกสารเงียบ)
- `navigator.share` ใน PWA standalone บน iOS · รุ่นขั้นต่ำของ iOS Safari จากหน้า Apple โดยตรง · ตัวเลข Chrome Android 111+ (BCD บอก 75 ซึ่งครอบคลุม)
- รูปแบบ user agent ของ LINE (ใช้ตรวจ in-app browser)
