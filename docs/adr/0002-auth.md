# ADR 0002 — การยืนยันตัวตน: Google + อีเมล OTP, โค้ดเชิญ, session, rate limit, consent

- สถานะ: **อนุมัติโดย boss 2026-11-16** — รับข้อเสนอ Q3 (iPhone ใช้ OTP อย่างเดียวได้ถ้า Google ไม่ผ่านการทดสอบเครื่องจริง), Q4 (boss ออกโค้ดเชิญด้วยสคริปต์), Q5 (Gmail SMTP เพดาน 400/วัน), Q6 (แจ้งเรื่อง backup ในประกาศความเป็นส่วนตัว) · วันที่ 2026-11-15 · ผู้เขียน: architect · **แก้ไข 2026-11-17** ตามผล spike S2 (รายละเอียดการทำ ไม่เปลี่ยนการตัดสินใจ — ดูบันทึกการแก้ไขท้ายไฟล์) · **แก้ไข 2026-11-18** ตาม [research/2026-11-18-r1-auth.md](../research/2026-11-18-r1-auth.md) และการอ่าน source better-auth 1.7.25 ของ architect (rate limit ของปลั๊กอิน OTP, จุดกั้นก่อนส่ง OTP, header IP, Gmail, ภาษาอีเมล, การลบ `verification`) — ดูบันทึกการแก้ไข · **แก้ไข 2026-11-20** ตาม R1.5 contract ที่ boss อนุมัติ: ผู้ออกโค้ดเป็นแอดมินผ่านหน้าเว็บ ([ADR 0007](0007-admin-invites.md)) สคริปต์เป็นทางสำรอง
- ฐานข้อเท็จจริง: [research/2026-11-15-auth.md](../research/2026-11-15-auth.md) · เอกสารที่ architect เปิดเพิ่ม 2026-11-15: [Better Auth database hooks](https://www.better-auth.com/docs/concepts/database) (hook `user.create.before(user, ctx)` คืน `false` = ยกเลิก · ตัวเลือก `generateId` — ใช้แบบฟังก์ชัน ดูบันทึกการแก้ไข), [Better Auth hooks ctx](https://www.better-auth.com/docs/concepts/hooks) (`ctx.getCookie`, `ctx.headers`, `ctx.path`, โยน `APIError` ได้)
- ขึ้นกับ: ADR 0001 (ฐานข้อมูล), ADR 0003 (ตาราง)

## บริบท

PRD E1: Google เป็นทางหลัก · อีเมล + OTP 6 หลักเป็นทางสำรอง · ไม่มีรหัสผ่าน · สมัครได้เฉพาะคนมีโค้ดเชิญ · session 60–90 วัน · OTP หมดอายุ 10 นาที เดาผิดเกิน 5 ครั้งต้องขอใหม่ · จำกัดการขอต่ออีเมลและต่อ IP · consent บันทึกเวลา+เวอร์ชัน · Google ต้องทำงานในแอปที่ติดตั้งบน iPhone จริง

ข้อเท็จจริงที่บังคับการออกแบบ: Better Auth 1.7.25 มี Google + email OTP · ค่าเริ่มต้น OTP 5 นาที/3 ครั้ง (ต้องตั้งเอง) · rate limit เริ่มต้นเก็บใน memory ซึ่งไม่เหมาะ serverless · จำกัดตามเส้นทาง+IP เท่านั้น ไม่มีต่ออีเมล · อ่าน IP จาก `X-Forwarded-For` (ปลอมได้) · ไม่มีปลั๊กอินโค้ดเชิญทางการ · Google redirect ในแอปที่ติดตั้งบน iOS มีรายงานว่า callback ไปลง Safari (แหล่งรอง) · Gmail SMTP 500 ฉบับ/วัน ต้องใช้ app password · Better Auth บอกห้าม await การส่งเมล ส่วน Vercel บอกว่า SMTP ต้อง await

**โค้ดเชิญ**

| ทางเลือก | ข้อดี | ข้อเสีย |
|---|---|---|
| A. `databaseHooks.user.create.before` ตรวจ+ใช้โค้ดจาก cookie ที่ตั้งไว้ก่อน (เลือก) | ใช้กลไกทางการ · คนไม่มีโค้ดไม่เกิดแถวในฐานข้อมูลเลย · ใช้ได้ทั้ง Google และ OTP เส้นเดียวกัน | ต้องตั้ง cookie ก่อนเริ่ม flow (เพิ่ม 1 endpoint) |
| B. ปลั๊กอินชุมชน `better-auth-invite` / `better-auth-invitation-only` | เขียนน้อย | ตัวหนึ่ง alpha อีกตัวยังไม่ได้ตรวจการดูแล · เพิ่ม dependency ในจุดที่เป็นความปลอดภัย |

**ที่เก็บตัวนับ rate limit**: memory (ใช้ไม่ได้บน serverless) · Redis/secondary storage (เพิ่มบริการภายนอก ต้องหาแพ็กเกจฟรี) · **database (เลือก)** — ใช้ฐานข้อมูลที่มีอยู่ ปริมาณคำขอ auth ต่ำมาก

**ผู้ส่งอีเมล**: Gmail SMTP (ตาม boss ข้อ 9 · ฟรี · ไม่แนะนำโดย Google/Vercel) · HTTP API เช่น Resend (Vercel แนะนำ · ยังไม่ได้วิจัยแพ็กเกจฟรี · ต้องมีโดเมน) → **ใช้ Gmail SMTP ตอนนี้ ผ่านชั้นที่สลับได้ด้วย env**

### 2. โค้ดเชิญ (ตาราง `invite_code` ใน ADR 0003, สร้างใน R1)

- รูปแบบ: 8 ตัวจาก `ABCDEFGHJKMNPQRSTUVWXYZ23456789` แสดงเป็น `XXXX-XXXX` · ไม่สนตัวพิมพ์/ขีด · เก็บเฉพาะ `code_hash = sha256(normalized)` · แสดงโค้ดครั้งเดียวตอนสร้าง
- ผู้ออกโค้ด v1: **แอดมิน (boss) ที่หน้า `/admin/invites` บนมือถือ** ตั้งแต่ R1.5 — สิทธิ์จากตาราง `app_admin` · กติกา D3 (อายุ 1/3/7/14 วัน · 1–10 ครั้ง · ป้าย 1–40 ตัว) · API และลำดับตรวจ: **ADR 0007** · ทางสำรอง: **boss รัน `scripts/invite.ts`** (`create --uses N --days D --label`, `list`, `revoke`) กติกาเดิม ไม่แก้
- วงจรชีวิต: `active` → `exhausted` (`uses_count = max_uses`) / `expired` (`expires_at` ผ่านแล้ว) / `revoked` (`revoked_at`) — สถานะคำนวณจากคอลัมน์ ไม่เก็บซ้ำ

| จุดตรวจ | ทำอะไร | ใช้โค้ดไหม |
|---|---|---|
| `POST /api/invite/check` | ตรวจว่า active → ตั้ง cookie `fcf_invite` (เก็บโค้ดดิบ, `HttpOnly; Secure; SameSite=Lax; Max-Age=1800; Path=/api/auth`) · ตอบ `ok` / `invalid` (ไม่แยกว่าไม่มีจริงหรือหมดอายุ เพื่อกันเดา) · rate limit ต่อ IP ด้วย `auth_throttle` (ข้อ 3 — route นี้ไม่ผ่าน limiter ของ Better Auth) · โค้ดมาใน body เท่านั้น (ลิงก์เชิญใช้ `#invite=` ตาม ADR 0006) | ไม่ |
| **จุดกั้นก่อนส่ง OTP** (`hooks.before` บน `/email-otp/send-verification-otp`) | ลำดับ: (1) `type` ไม่ใช่ `"sign-in"` → 400 · (2) `auth_throttle` ต่ออีเมล → 429 · (3) เพดานรายวันเต็ม → 503 `email_unavailable` · (4) **ไม่มีผู้ใช้อีเมลนี้ และไม่มี cookie `fcf_invite` ที่ยัง active** (SELECT เท่านั้น ไม่นับสิทธิ์) → คืน `ctx.json({ success: true })` ทันที **ไม่สร้าง OTP ไม่ส่งเมล** · ผ่านหมด → ปลั๊กอินทำงานต่อ | ไม่ |
| hook `user.create.before` | อ่าน `ctx.getCookie("fcf_invite")` → `UPDATE invite_code SET uses_count = uses_count + 1 WHERE code_hash = ? AND uses_count < max_uses AND expires_at > now AND revoked_at IS NULL` (คำสั่งเดียว atomic) → 0 แถว = โยน `APIError` `invite_required` · สำเร็จ = ใส่ `invite_code_id` ให้ผู้ใช้ · **`ctx` เป็น `null`** (ชนิด `GenericEndpointContext \| null` — ถูกเรียกนอก endpoint) → โยน `invite_required` เสมอ (ปิดไว้ก่อน) | **ใช่** (จุดเดียวที่ใช้) |
| ผู้ใช้เดิมล็อกอิน | ไม่ตรวจโค้ด | — |

หมายเหตุ: cookie ไม่ต้องเซ็นเพราะ hook ตรวจกับฐานข้อมูลอีกครั้ง · ถ้าสร้างผู้ใช้ล้มหลังนับโค้ดแล้ว ยอมเสีย 1 สิทธิ์ (boss ออกใหม่ได้) · ถ้า `ctx.getCookie` ใช้ไม่ได้ใน database hook (ยังไม่ได้ทดสอบ) ให้ใช้ `hooks.before` บนเส้นทางสร้างผู้ใช้แทนโดยหลักการเดิม — platform ยืนยันใน R1 (spike A1)

**กันเดาว่าอีเมลไหนมีบัญชี (ตัดสินแล้ว):** ขั้น (4) ตอบ **200 `{ success: true }` เหมือนกรณีส่งจริงทุกไบต์** — ตรงกับที่ปลั๊กอินทำเองเมื่อ `disableSignUp: true` (`plugins/email-otp/routes.mjs` บรรทัด 103–108) · before hook ที่คืน object ที่ไม่มี `context` ถูกใช้เป็นคำตอบทันที (`api/dispatch.mjs` บรรทัด 111–124) · ขั้น (2) และ (3) ตรวจ**ก่อน**รู้ว่ามีบัญชีไหม และขั้น (2) นับทุกคำขอที่ผ่านขั้น (1) ไม่ว่ามีบัญชีหรือไม่ → 429/503 ไม่บอกอะไรเกี่ยวกับอีเมลนั้น · ตัวนับรายวันนับเฉพาะเมลที่ส่งจริง · ยืนยัน OTP ของอีเมลที่ถูกกั้นได้ `INVALID_OTP` เหมือนรหัสผิด (ไม่มีแถว `verification`) · เวลาตอบ: ส่งเมลแบบ `waitUntil` ทำให้สองทางเร็วพอกัน — ถ้า spike A4 ไม่ผ่านจนต้อง `await` การส่ง ทางที่ถูกกั้นตอบเร็วกว่าราว 1–2 วิ (เดาได้) → platform หน่วงทางที่ถูกกั้นให้ใกล้เคียง หรือบันทึกเป็นความเสี่ยงที่รับไว้ให้ security-privacy ตรวจ · UI จอ OTP บอกเสมอว่า "ถ้ายังไม่เคยสมัคร ต้องใส่โค้ดเชิญก่อน" (ผู้ไม่มีโค้ดจะไม่ได้เมล)

### 3. Rate limit

- Better Auth `rateLimit.storage: "database"` (ตาราง `rate_limit` อยู่ใน migration แรกแล้ว · `last_request` เป็น epoch ms ชนิด `double precision` ตาม ADR 0001) · **header IP: ใช้ค่าเริ่ม `ipAddressHeaders: ["x-forwarded-for"]` ไม่ต้องตั้ง** — Vercel เขียนทับ header นี้ด้วย IP สาธารณะของไคลเอนต์ ไม่ส่งต่อค่าที่ไคลเอนต์ส่งมา ([Vercel request headers](https://vercel.com/docs/headers/request-headers) ตาม research 2026-11-18) · เงื่อนไข: ไม่มี proxy/CDN อื่นซ้อนหน้า Vercel (ถ้าเพิ่มต้องทบทวน)
- **ลำดับความสำคัญของกฎใน better-auth 1.7.25** (`api/rate-limiter/index.mjs` บรรทัด 237–284): กฎพิเศษในตัว (`/sign-in*` 3/10 วิ · `/email-otp/send-verification-otp` 3/60 วิ) → ทับด้วยกฎของปลั๊กอิน (`emailOTP` 3/60 วิ **ค่าเดียวทุกเส้นทางของปลั๊กอิน**) → ทับด้วย `rateLimit.customRules` (มาทีหลังสุด ชนะ) · จึงตั้งรายเส้นทางด้วย `customRules`:
  - `"/email-otp/send-verification-otp": { window: 600, max: 5 }` · `"/sign-in/email-otp": { window: 600, max: 10 }` · เส้นทางอื่นของปลั๊กอินที่ไม่ใช้คงค่าในตัว 3/60 วิ · `/sign-in/social` คงกฎพิเศษ 3/10 วิ
  - หน้าต่างนับจาก**คำขอล่าสุดที่ผ่าน** ไม่ใช่ช่วงเวลาตายตัว (ครบ `max` แล้วรอ `window` นับจากครั้งที่ผ่านล่าสุด) · ถูกจำกัดตอบ 429 + header `X-Retry-After` (วินาที)
- ต่ออีเมล/ทั้งระบบ/invite: ตาราง `auth_throttle` ของเราเอง (ADR 0003) ตรวจในจุดกั้นก่อนส่ง OTP (ข้อ 2) และใน `/api/invite/check` · key: `otp-email:<sha256(lower(email))>` · `otp-day:<YYYY-MM-DD UTC>` · **`invite-ip:<sha256(ip)>`** (ใหม่ — route ของเราไม่ผ่าน limiter ของ Better Auth) · **`admin-invite:<sha256(userId)>`** (R1.5 — ออกโค้ด ≤ 20 ครั้ง/24 ชม. ต่อแอดมิน ADR 0007) · ไม่เก็บอีเมลหรือ IP ดิบ · ถูกจำกัดตอบ 429 + `X-Retry-After` **รูปเดียวกับ Better Auth** ให้ UI อ่านที่เดียว

| เส้นทาง | ต่อ IP | ต่ออีเมล (`auth_throttle`) |
|---|---|---|
| ขอส่ง OTP | 5 ครั้ง / 10 นาที (`customRules`) | ห่างกัน ≥ 60 วิ · ≤ 5 ครั้ง/ชม. · ≤ 10 ครั้ง/วัน |
| ยืนยัน OTP | 10 ครั้ง / 10 นาที (`customRules`) | ผิด 5 ครั้งต่อรหัส (ในตัว `allowedAttempts`) |
| `/api/invite/check` | 10 ครั้ง / 10 นาที (`auth_throttle` key `invite-ip:`) | — |
| ทั้งระบบ | — | OTP ≤ `OTP_DAILY_CAP` (ค่าเริ่ม 400) ฉบับ/วัน (วันตาม UTC) · เกินแล้วตอบ **503** `{ code: "email_unavailable" }` ให้ UI ชวนใช้ Google |

ตัวเลขข้างบนเป็นค่าเริ่ม ปรับใน contract ได้ (แก้ง่าย) · UI แสดง "รอ mm:ss" จาก `X-Retry-After` · ข้อจำกัดที่รับไว้: เพดานรายวันนับเป็นวันปฏิทิน แต่ลิมิตของ Gmail อาจเป็นช่วง 24 ชม. เลื่อน (เอกสารไม่ระบุ) — ส่งช่วงข้ามเที่ยงคืนได้เกิน 400 ใน 24 ชม. ไม่น่าเกิดกับกลุ่ม ~10 คน

### 4. ชั้นส่งอีเมล (`src/lib/email/**` — เสนอให้เป็นของ ops-release)

- interface เดียว `sendEmail({ to, subject, text, html }) → Promise<void>` · Better Auth `sendVerificationOTP` เรียกผ่านชั้นนี้เท่านั้น
- เลือกตัวส่งด้วย `EMAIL_TRANSPORT`: `smtp` (nodemailer, พอร์ต 465/587) · `log` (dev/เทสต์ พิมพ์ลง log ไม่ส่งจริง) · `http` (ว่างไว้ เพิ่มเมื่อ boss ซื้อโดเมน) · เปลี่ยนผู้ส่ง = แก้ env ไม่แก้โค้ด auth
- บน Vercel: ครอบ promise ที่ `await` การส่งด้วย `waitUntil` ให้ request ตอบทันที (ข้อเสนอจากวิจัย · ทดสอบแล้วใน R1 spike A4 (2026-11-19 บน preview + Gmail จริง): เมลถึง 12/12 ฉบับที่รับไว้ · 8 ครั้งที่เหลือถูก limiter ต่อ IP ตอบ 429 ก่อนส่ง ไม่ใช่เมลหาย — ดู OPERATIONS ข้อ 8.ฉ)
- ~~ที่อยู่/พอร์ต SMTP ของ Gmail ยังไม่ได้ยืนยัน~~ **ยืนยันแล้ว** (research 2026-11-18, หน้า Workspace "ส่งอีเมลจากเครื่องพิมพ์ สแกนเนอร์ หรือแอป"): `smtp.gmail.com` พอร์ต 465 (SSL) หรือ 587 (STARTTLS) · ค่ายังอยู่ใน env (`SMTP_HOST` `SMTP_PORT` ฯลฯ — ops ตั้งชื่อ) ไม่ฝังในโค้ด

### 6. Consent

- ตาราง `consent_record` (ADR 0003) เก็บ `notice_version` + `accepted_at` + `locale` · ประกาศมีเวอร์ชันเป็นค่าคงที่ในโค้ด `PRIVACY_NOTICE_VERSION` (เช่น `2026-11-15`)
- ทุก API ข้อมูล (ยกเว้น auth, `/api/me`, `/api/consent`, ลบบัญชี, API แอดมิน `/api/admin/**` ที่ไม่แตะข้อมูลสุขภาพ — ADR 0007) ตอบ `403 consent_required` ถ้าผู้ใช้ไม่มี consent ของเวอร์ชันปัจจุบัน · เปลี่ยนเวอร์ชันประกาศ = ทุกคนต้องกดยินยอมใหม่
- consent บันทึกได้เฉพาะออนไลน์ (ไม่เข้าคิว) · ถอน consent ของผู้ใช้ที่ยินยอมแล้ว = ลบบัญชี · **ผู้ใช้เดิมที่ยังไม่ยินยอมประกาศฉบับใหม่** (boss 2026-11-20) เลือกได้ว่า (1) ออกจากระบบ — ข้อมูลยังอยู่ ยินยอมภายหลังแล้วใช้ต่อได้ หรือ (2) ลบบัญชีพร้อมข้อมูลทั้งหมด (ยืนยันก่อน) · ใช้แอปต่อไม่ได้จนกว่าจะยินยอมหรือออกจากระบบ · ระยะเวลาเก็บข้อมูลของกรณีออกจากระบบยังไม่ตัดสิน (PRD §9 ข้อ 4)

### 7. ออกจากระบบและลบบัญชี

- ออกจากระบบ: Better Auth sign-out (ลบ session แถวนั้น) + ไคลเอนต์ล้างข้อมูลตาม ADR 0004 ข้อ 8 (รวม `clearUserCaches()` ตาม ADR 0005) · หน้า HTML ต้องไม่มีข้อมูลส่วนตัว และหน้าต้องตรวจสถานะล็อกอินฝั่งไคลเอนต์ด้วยเสมอ (ADR 0005 กติกา 1) · ลำดับขั้นฝั่งไคลเอนต์ การพาไปจอที่ถูก และจอยินดีต้อนรับตอนออฟไลน์: **ADR 0006**
- ลบบัญชี `DELETE /api/me` (ออนไลน์เท่านั้น): ใน transaction เดียว ลบ `verification` และ `auth_throttle` ที่ผูกกับอีเมล → ลบ `user` (cascade ตาม ADR 0003) · เทสต์ R1 ตรวจว่าทุกตารางที่มี `user_id` เหลือ 0 แถวของคนนั้น
- **ยืนยันแล้ว (2026-11-18) ว่าแผนนี้ครอบคลุม**: `deleteUser` ของ Better Auth ลบแค่ `session` `account` `user` **ไม่แตะ `verification`** และเช็ก "session สด" (`freshAge` 1 วัน — session 90 วันลบไม่ได้) → **ไม่เปิด `user.deleteUser`** ใช้ `DELETE /api/me` ของเราเท่านั้น ซึ่งลบ `verification` เองอยู่แล้ว · รายละเอียด:
  - แถว OTP: `identifier = "<type>-otp-<lower(email)>"` (`plugins/email-otp/utils.mjs` บรรทัด 4–6) → ลบด้วย**รายการ identifier ตรงตัว** ของทุก type ของปลั๊กอิน (`sign-in` `email-verification` `forget-password` `change-email`) · **ห้ามใช้ `LIKE`** (`_` ในอีเมลเป็น wildcard)
  - แถว OAuth state/PKCE (`storeStateStrategy: "database"`): identifier สุ่ม ไม่ผูกอีเมล มีวันหมดอายุ (ไม่ได้ตรวจตัวเลข) — ยอมรับ ไม่ต้องลบ · security-privacy ยืนยันว่าค่าในแถวไม่มีอีเมล
  - `auth_throttle`: ลบ key `otp-email:<sha256(lower(email))>` และ `admin-invite:<sha256(userId)>` (R1.5) · `otp-day:` และ `invite-ip:` ไม่ผูกผู้ใช้ ไม่ลบ
  - `app_admin` (R1.5) หายด้วย cascade จาก `user`
  - **ป้ายของโค้ดที่บัญชีใช้สมัคร** (R1.5 · boss ตัดสิน 2026-11-20): ก่อนลบ `user` อ่าน `user.invite_code_id` → ถ้ามี ตั้ง `invite_code.label = '—'` (`DELETED_INVITE_LABEL`) เฉพาะแถวนั้น (รวมโค้ดหลายสิทธิ์ที่คนอื่นใช้ด้วย) · แถว `invite_code` ไม่ลบ · เหตุ: ป้ายที่แอดมินตั้งอาจเป็นชื่อเล่นของผู้สมัคร (ADR 0007 ข้อ 3) · ประกาศความเป็นส่วนตัวเพิ่มบรรทัดเรื่องนี้และเปลี่ยน `PRIVACY_NOTICE_VERSION` (ข้อ 6: ทุกคนยินยอมใหม่ 1 ครั้ง)
  - `session` และ `account` หายด้วย cascade จาก `user` · ตอบพร้อม `Set-Cookie` ลบ cookie session

## ผลที่ตามมา

- ง่ายขึ้น: สมัครทั้งสองทางผ่านจุดกั้นเดียว · เปลี่ยนผู้ส่งเมลด้วย env · rate limit ใช้ฐานข้อมูลที่มีอยู่
