# ADR 0002 — การยืนยันตัวตน: Google + อีเมล OTP, โค้ดเชิญ, session, rate limit, consent

- สถานะ: **อนุมัติโดย boss 2026-11-16** — รับข้อเสนอ Q3 (iPhone ใช้ OTP อย่างเดียวได้ถ้า Google ไม่ผ่านการทดสอบเครื่องจริง), Q4 (boss ออกโค้ดเชิญด้วยสคริปต์), Q5 (Gmail SMTP เพดาน 400/วัน), Q6 (แจ้งเรื่อง backup ในประกาศความเป็นส่วนตัว) · วันที่ 2026-11-15 · ผู้เขียน: architect
- ฐานข้อเท็จจริง: [research/2026-11-15-auth.md](../research/2026-11-15-auth.md) · เอกสารที่ architect เปิดเพิ่ม 2026-11-15: [Better Auth database hooks](https://www.better-auth.com/docs/concepts/database) (hook `user.create.before(user, ctx)` คืน `false` = ยกเลิก · `generateId: "uuid"`), [Better Auth hooks ctx](https://www.better-auth.com/docs/concepts/hooks) (`ctx.getCookie`, `ctx.headers`, `ctx.path`, โยน `APIError` ได้)
- ขึ้นกับ: ADR 0001 (ฐานข้อมูล), ADR 0003 (ตาราง)

## บริบท

PRD E1: Google เป็นทางหลัก · อีเมล + OTP 6 หลักเป็นทางสำรอง · ไม่มีรหัสผ่าน · สมัครได้เฉพาะคนมีโค้ดเชิญ · session 60–90 วัน · OTP หมดอายุ 10 นาที เดาผิดเกิน 5 ครั้งต้องขอใหม่ · จำกัดการขอต่ออีเมลและต่อ IP · consent บันทึกเวลา+เวอร์ชัน · Google ต้องทำงานในแอปที่ติดตั้งบน iPhone จริง

ข้อเท็จจริงที่บังคับการออกแบบ: Better Auth 1.7.25 มี Google + email OTP · ค่าเริ่มต้น OTP 5 นาที/3 ครั้ง (ต้องตั้งเอง) · rate limit เริ่มต้นเก็บใน memory ซึ่งไม่เหมาะ serverless · จำกัดตามเส้นทาง+IP เท่านั้น ไม่มีต่ออีเมล · อ่าน IP จาก `X-Forwarded-For` (ปลอมได้) · ไม่มีปลั๊กอินโค้ดเชิญทางการ · Google redirect ในแอปที่ติดตั้งบน iOS มีรายงานว่า callback ไปลง Safari (แหล่งรอง) · Gmail SMTP 500 ฉบับ/วัน ต้องใช้ app password · Better Auth บอกห้าม await การส่งเมล ส่วน Vercel บอกว่า SMTP ต้อง await

## ทางเลือกที่พิจารณา

**โค้ดเชิญ**

| ทางเลือก | ข้อดี | ข้อเสีย |
|---|---|---|
| A. `databaseHooks.user.create.before` ตรวจ+ใช้โค้ดจาก cookie ที่ตั้งไว้ก่อน (เลือก) | ใช้กลไกทางการ · คนไม่มีโค้ดไม่เกิดแถวในฐานข้อมูลเลย · ใช้ได้ทั้ง Google และ OTP เส้นเดียวกัน | ต้องตั้ง cookie ก่อนเริ่ม flow (เพิ่ม 1 endpoint) |
| B. ปลั๊กอินชุมชน `better-auth-invite` / `better-auth-invitation-only` | เขียนน้อย | ตัวหนึ่ง alpha อีกตัวยังไม่ได้ตรวจการดูแล · เพิ่ม dependency ในจุดที่เป็นความปลอดภัย |
| C. สร้างผู้ใช้ได้ทุกคน แล้วบังคับกรอกโค้ดหลังล็อกอิน | ไม่ต้องพา cookie ข้าม redirect | เก็บอีเมลของคนที่ไม่ได้รับเชิญ (ขัดหลักเก็บเท่าที่จำเป็น) · ต้องมีงานล้างผู้ใช้ค้าง · ขัดเกณฑ์ "ไม่มีโค้ดสมัครไม่ได้" |

**ที่เก็บตัวนับ rate limit**: memory (ใช้ไม่ได้บน serverless) · Redis/secondary storage (เพิ่มบริการภายนอก ต้องหาแพ็กเกจฟรี) · **database (เลือก)** — ใช้ฐานข้อมูลที่มีอยู่ ปริมาณคำขอ auth ต่ำมาก

**ผู้ส่งอีเมล**: Gmail SMTP (ตาม boss ข้อ 9 · ฟรี · ไม่แนะนำโดย Google/Vercel) · HTTP API เช่น Resend (Vercel แนะนำ · ยังไม่ได้วิจัยแพ็กเกจฟรี · ต้องมีโดเมน) → **ใช้ Gmail SMTP ตอนนี้ ผ่านชั้นที่สลับได้ด้วย env**

## การตัดสินใจ

### 1. ค่าตั้งของ Better Auth (platform, `src/lib/auth/**`)

| เรื่อง | ค่า |
|---|---|
| adapter | `@better-auth/drizzle-adapter` provider ตาม ADR 0001 (`pg`) · ตารางสร้างด้วย `npx auth@latest generate` แล้วเข้า migration ปกติ |
| id | `advanced.database.generateId: "uuid"` → `user.id` เป็น UUID (ตรงกับ FK ของทุกตารางใน ADR 0003) · R1 ตรวจผลจาก CLI ว่าเป็น uuid จริง |
| Google | `socialProviders.google` scope `openid email profile` เท่านั้น · redirect `/api/auth/callback/google` · ตั้ง `BETTER_AUTH_URL` ทุกสภาพแวดล้อม |
| Email OTP | `otpLength: 6` · `expiresIn: 600` · `allowedAttempts: 5` · `storeOTP: "hashed"` · `disableSignUp: false` (ให้ hook โค้ดเชิญเป็นคนกั้น) |
| Session | `expiresIn: 90 วัน` · `updateAge: 1 วัน` (ใช้แอปอย่างน้อยทุก 90 วันไม่ต้องล็อกอินใหม่) · `cookieCache` ปิด หรือ ≤ 5 นาที · cookie `HttpOnly; Secure; SameSite=Lax` · session เก็บในตาราง จึงเพิกถอนได้ |
| ไม่มี | รหัสผ่าน · PIN · passkey (P2 เพิ่มเป็นปลั๊กอินได้ภายหลัง) |

### 2. โค้ดเชิญ (ตาราง `invite_code` ใน ADR 0003, สร้างใน R1)

- รูปแบบ: 8 ตัวจาก `ABCDEFGHJKMNPQRSTUVWXYZ23456789` แสดงเป็น `XXXX-XXXX` · ไม่สนตัวพิมพ์/ขีด · เก็บเฉพาะ `code_hash = sha256(normalized)` · แสดงโค้ดครั้งเดียวตอนสร้าง
- ผู้ออกโค้ด v1: **boss รัน `scripts/invite.ts`** (`create --uses N --days D --label`, `list`, `revoke`) · ไม่มีหน้าแอดมินใน v1
- วงจรชีวิต: `active` → `exhausted` (`uses_count = max_uses`) / `expired` (`expires_at` ผ่านแล้ว) / `revoked` (`revoked_at`) — สถานะคำนวณจากคอลัมน์ ไม่เก็บซ้ำ

| จุดตรวจ | ทำอะไร | ใช้โค้ดไหม |
|---|---|---|
| `POST /api/invite/check` | ตรวจว่า active → ตั้ง cookie `fcf_invite` (เก็บโค้ดดิบ, `HttpOnly; Secure; SameSite=Lax; Max-Age=1800; Path=/api/auth`) · ตอบ `ok` / `invalid` (ไม่แยกว่าไม่มีจริงหรือหมดอายุ เพื่อกันเดา) · rate limit ต่อ IP | ไม่ |
| hook `user.create.before` | อ่าน `ctx.getCookie("fcf_invite")` → `UPDATE invite_code SET uses_count = uses_count + 1 WHERE code_hash = ? AND uses_count < max_uses AND expires_at > now AND revoked_at IS NULL` (คำสั่งเดียว atomic) → 0 แถว = โยน `APIError` `invite_required` · สำเร็จ = ใส่ `invite_code_id` ให้ผู้ใช้ | **ใช่** (จุดเดียวที่ใช้) |
| ผู้ใช้เดิมล็อกอิน | ไม่ตรวจโค้ด | — |

หมายเหตุ: cookie ไม่ต้องเซ็นเพราะ hook ตรวจกับฐานข้อมูลอีกครั้ง · ถ้าสร้างผู้ใช้ล้มหลังนับโค้ดแล้ว ยอมเสีย 1 สิทธิ์ (boss ออกใหม่ได้) · ถ้า `ctx.getCookie` ใช้ไม่ได้ใน database hook (ยังไม่ได้ทดสอบ) ให้ใช้ `hooks.before` บนเส้นทางสร้างผู้ใช้แทนโดยหลักการเดิม — platform ยืนยันใน R1

### 3. Rate limit

- Better Auth `rateLimit.storage: "database"` (ตาราง `rateLimit` เข้า migration) · `ipAddressHeaders` ตั้งตาม header ที่ Vercel รับรอง (**ยังไม่ได้ยืนยันชื่อ header** — security-privacy เปิดเอกสาร Vercel ใน R1)
- ต่ออีเมล/ทั้งระบบ: ตาราง `auth_throttle` ของเราเอง (ADR 0003) ตรวจใน `hooks.before` ของเส้นทางขอ OTP · key ใช้ `sha256(lower(email))` ไม่เก็บอีเมลดิบ

| เส้นทาง | ต่อ IP (Better Auth) | ต่ออีเมล (`auth_throttle`) |
|---|---|---|
| ขอส่ง OTP | 5 ครั้ง / 10 นาที | ห่างกัน ≥ 60 วิ · ≤ 5 ครั้ง/ชม. · ≤ 10 ครั้ง/วัน |
| ยืนยัน OTP | 10 ครั้ง / 10 นาที | ผิด 5 ครั้งต่อรหัส (ในตัว) |
| `/api/invite/check` | 10 ครั้ง / 10 นาที | — |
| ทั้งระบบ | — | OTP ≤ `OTP_DAILY_CAP` (ค่าเริ่ม 400) ฉบับ/วัน ต่ำกว่าลิมิต Gmail 500 · เกินแล้วตอบ `email_unavailable` ให้ UI ชวนใช้ Google |

ตัวเลขข้างบนเป็นค่าเริ่ม ปรับใน contract ได้ (แก้ง่าย) · ตอบ 429 พร้อมเวลารอ ให้ UI แสดง "รอ mm:ss"

### 4. ชั้นส่งอีเมล (`src/lib/email/**` — เสนอให้เป็นของ ops-release)

- interface เดียว `sendEmail({ to, subject, text, html }) → Promise<void>` · Better Auth `sendVerificationOTP` เรียกผ่านชั้นนี้เท่านั้น
- เลือกตัวส่งด้วย `EMAIL_TRANSPORT`: `smtp` (nodemailer, พอร์ต 465/587) · `log` (dev/เทสต์ พิมพ์ลง log ไม่ส่งจริง) · `http` (ว่างไว้ เพิ่มเมื่อ boss ซื้อโดเมน) · เปลี่ยนผู้ส่ง = แก้ env ไม่แก้โค้ด auth
- บน Vercel: ครอบ promise ที่ `await` การส่งด้วย `waitUntil` ให้ request ตอบทันที (ข้อเสนอจากวิจัย **ยังไม่ทดสอบ** — ops ยืนยันใน R1 ว่าเมลถึงจริง 20/20 ครั้ง)
- ที่อยู่/พอร์ต SMTP ของ Gmail **ยังไม่ได้ยืนยัน** → อยู่ใน env ทั้งหมด ops เปิดเอกสาร Google ก่อนตั้ง

### 5. Google ในแอปที่ติดตั้งบน iOS

แผน: ใช้ redirect flow มาตรฐานก่อน · OTP ใช้ได้เสมอเพราะไม่ออกนอก origin · ทดสอบเครื่องจริงใน R1 ตามตาราง แล้วเลือกทางแก้ตามลำดับจนกว่าจะผ่าน

| ลำดับ | ทาง | หมายเหตุ |
|---|---|---|
| 1 | redirect มาตรฐาน | ถ้า callback กลับเข้าแอปและล็อกอินอยู่ → จบ |
| 2 | Google ID token flow ของ Better Auth (ไม่ redirect) | ต้องยืนยันว่าปุ่ม Google ฝั่งไคลเอนต์ทำงานใน standalone iOS |
| 3 | ซ่อนปุ่ม Google เมื่อ `display-mode: standalone` บน iOS ให้ใช้ OTP | ทางถอยสุดท้าย — ทำให้เกณฑ์ PRD ข้อ E1 ไม่ผ่าน ต้องให้ boss อนุมัติ (Q4) |

ตารางทดสอบเครื่องจริง R1 (QA + boss): iPhone รุ่น iOS ล่าสุดที่กลุ่มมี และรุ่นต่ำสุดที่รองรับ (ADR 0004) × {Safari แท็บ, แอปที่ติดตั้ง} × {สมัครใหม่ด้วยโค้ด, ล็อกอินบัญชีเดิม, OTP} + Android Chrome {แท็บ, ติดตั้ง} · ผลที่ต้องจด: กลับเข้าแอปไหม · ในแอปล็อกอินอยู่ไหม · cookie `fcf_invite` ไปถึง callback ไหม · ปิดแอปเปิดใหม่ยังล็อกอินไหม

### 6. Consent

- ตาราง `consent_record` (ADR 0003) เก็บ `notice_version` + `accepted_at` + `locale` · ประกาศมีเวอร์ชันเป็นค่าคงที่ในโค้ด `PRIVACY_NOTICE_VERSION` (เช่น `2026-11-15`)
- ทุก API ข้อมูล (ยกเว้น auth, `/api/me`, `/api/consent`, ลบบัญชี) ตอบ `403 consent_required` ถ้าผู้ใช้ไม่มี consent ของเวอร์ชันปัจจุบัน · เปลี่ยนเวอร์ชันประกาศ = ทุกคนต้องกดยินยอมใหม่
- consent บันทึกได้เฉพาะออนไลน์ (ไม่เข้าคิว) · v1 ถอน consent = ลบบัญชี

### 7. ออกจากระบบและลบบัญชี

- ออกจากระบบ: Better Auth sign-out (ลบ session แถวนั้น) + ไคลเอนต์ล้างข้อมูลตาม ADR 0004
- ลบบัญชี `DELETE /api/me` (ออนไลน์เท่านั้น): ใน transaction เดียว ลบ `verification` และ `auth_throttle` ที่ผูกกับอีเมล → ลบ `user` (cascade ตาม ADR 0003) · เทสต์ R1 ตรวจว่าทุกตารางที่มี `user_id` เหลือ 0 แถวของคนนั้น

## ผลที่ตามมา

- ง่ายขึ้น: สมัครทั้งสองทางผ่านจุดกั้นเดียว · เปลี่ยนผู้ส่งเมลด้วย env · rate limit ใช้ฐานข้อมูลที่มีอยู่
- ยากขึ้น: ต้องเขียน `auth_throttle` และ hook เอง · iOS standalone อาจต้องทำทางแก้ข้อ 5 ซึ่งยังประเมินงานไม่ได้
- ต้องทำตาม: security-privacy ตรวจ R1 ครบทุกแถวของตารางข้อ 3 · ไม่ log อีเมลดิบหรือ OTP ใน production · ทุก endpoint ใหม่ต้องเรียก `requireUser()` (+ `requireConsent()`) จาก `src/lib/auth/server`
