# VERSIONING — กติกาเลขรุ่นและการออกรุ่น

> เจ้าของ: ops-release · ใช้ [SemVer 2.0.0](https://semver.org/spec/v2.0.0.html) และรูปแบบ CHANGELOG ของ [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/) · ที่มา: PROCESS.md กติกาข้อ 7

## หลักการ

- เลขรุ่นรูป `X.Y.Z` เริ่มที่ **0.1.0** (รอบ R0 ปิดที่ 0.1.0) — ก่อนออกรุ่นแรก `package.json` เป็น `0.0.0`
- **ชื่อรอบ (R0, R1 ...) ไม่ใช่เลขรุ่น** — รอบเป็นหน่วยงานของทีม เลขรุ่นเป็นหน่วยของผู้ใช้ รอบหนึ่งอาจออก 1 รุ่นหรือไม่ออกเลย (รอบเอกสารล้วนไม่ออกรุ่น)
- 1 pull request ของรอบ = อย่างมาก 1 รุ่น · Lead เสนอเลขรุ่นใน pull request · boss อนุมัติด้วยการกด merge
- ไม่มี pre-release (`-rc.1`) และไม่มี `v` นำหน้าใน `package.json` (tag บน Git มี `v` นำหน้า: `v0.1.0`)

## เลขไหนขยับเมื่อไร

ตราบที่ยังเป็น `0.y.z` (ก่อน v1.0.0) ความหมายขยับลงหนึ่งขั้นตาม SemVer ข้อ 4 — ผู้ใช้จริงมีแค่กลุ่มเพื่อนกลุ่มเล็ก และเรายังเปลี่ยนรูปทรงได้

| เลข | ขยับเมื่อ | ตัวอย่างของโปรเจกต์นี้ |
|---|---|---|
| **MAJOR** (`X`) | เปลี่ยนแบบที่ผู้ใช้เดิมต้องทำอะไรเพิ่มหรือข้อมูลเดิมใช้ไม่ได้ · เปิดใช้จริงให้กลุ่มกว้างขึ้นครั้งแรก = **1.0.0** (boss ตัดสิน) | migration ที่ย้อนข้อมูลไม่ได้ · เปลี่ยนวิธีเข้าสู่ระบบจนต้องผูกบัญชีใหม่ · เปลี่ยนรูปแบบไฟล์ส่งออก CSV แบบไม่เข้ากันกับของเดิม |
| **MINOR** (`Y`) | มีความสามารถใหม่ที่ผู้ใช้เห็น · ระหว่าง 0.y.z ใช้ขยับเมื่อมีการเปลี่ยนที่ไม่เข้ากันกับของเดิมด้วย | จบรอบฟีเจอร์ (R1 บัญชี, R2 คลังท่า, R3 จดการออกกำลังกาย ...) · ธีม/ภาษาใหม่ · หน้าจอใหม่ |
| **PATCH** (`Z`) | แก้ข้อผิดพลาดหรือปรับเล็กน้อยโดยพฤติกรรมที่ผู้ใช้พึ่งอยู่ไม่เปลี่ยน | แก้บั๊ก คำผิด ปรับคอนทราสต์ แก้ประสิทธิภาพ อัปเดต dependency เพื่อความปลอดภัย |

ไม่ต้องออกรุ่น: เอกสารล้วน · การแก้ CI/เครื่องมือที่ไม่กระทบแอป (ถ้าอยากบันทึกไว้ ใส่ใน `[Unreleased]` ได้ แล้วออกรุ่นพร้อมงานถัดไป)

แผนที่คาด (ไม่ผูกมัด): R0 → 0.1.0 · R1 → 0.2.0 · R2 → 0.3.0 · R3 → 0.4.0 · R4 → 0.5.0 · R5 → 0.6.0 · R6 → 1.0.0 หรือ 0.7.0 ตามที่ boss ตัดสิน

## CHANGELOG.md

- มีหัว `## [Unreleased]` เสมอ · ทุก pull request ที่เปลี่ยนสิ่งที่ผู้ใช้หรือผู้ดูแลเห็น เพิ่มบรรทัดใต้ `[Unreleased]` ในหมวด `Added` / `Changed` / `Deprecated` / `Removed` / `Fixed` / `Security`
- เขียนเป็นภาษาไทย ประโยคเดียวต่อรายการ บอกสิ่งที่เปลี่ยนจากมุมผู้ใช้/ผู้ดูแล ไม่ใส่ความลับ ชื่อบัญชี หรือรายละเอียดช่องโหว่ที่ยังไม่ได้แก้
- ตอนออกรุ่น เนื้อหาใต้ `[Unreleased]` ย้ายไปอยู่ใต้ `## [X.Y.Z] - YYYY-MM-DD` และ `[Unreleased]` เปิดว่างไว้ใหม่ (สคริปต์ทำให้)

## ขั้นตอนออกรุ่น

ผู้ทำ: **Lead** (boss ไม่ต้องรันคำสั่งใด)

1. ใน branch ของรอบ รัน `npx tsx scripts/release.ts X.Y.Z` (เพิ่ม `--date YYYY-MM-DD` ถ้าไม่ใช้วันนี้ตามเวลา UTC, เพิ่ม `--dry-run` เพื่อดูก่อน) สคริปต์แก้ `CHANGELOG.md`, `version` ใน `package.json` และ `package-lock.json` — **ไม่ commit ไม่ tag ไม่ push**
2. ตรวจ `git diff` แล้ว commit (เช่น `chore(release): vX.Y.Z`) รวมไปใน pull request ของรอบ และระบุเลขรุ่นที่เสนอในคำอธิบาย PR
3. CI เขียว → boss กด merge
4. workflow `release.yml` ทำงานเองบน `main`: อ่าน `version` จาก `package.json` ถ้ายังไม่มี GitHub release ชื่อ `vX.Y.Z` จะสร้าง tag ที่ commit ที่ merge และ GitHub release โดยใช้เนื้อหาของรุ่นนั้นจาก CHANGELOG · ถ้ามีแล้วจะข้าม (merge ที่ไม่เปลี่ยนเลขรุ่นจึงไม่ออกรุ่นซ้ำ) · ถ้าเลขรุ่นไม่มีหัวข้อใน CHANGELOG งานนี้จะแดง (ไม่ออกรุ่นที่ไม่มีบันทึก)
5. ตรวจว่า release ขึ้นที่หน้า Releases ของ repo (Lead ตรวจและรายงาน boss)

## ตรวจโดยเทสต์

`scripts/release.test.ts` ตรวจว่า `package.json` มี `version` ที่มีหัวข้อของตัวเองใน `CHANGELOG.md` (ยกเว้น `0.0.0`) และมีหัว `[Unreleased]` — ลืมแก้ CHANGELOG ตอนเปลี่ยนเลขรุ่น CI จะแดงก่อน merge

## ถ้าออกรุ่นผิด

ห้ามแก้ tag ที่ออกแล้ว (ย้าย tag ทำให้คนที่ดึงไปแล้วสับสน) · ออกรุ่น PATCH ถัดไปพร้อมบันทึกการแก้ · ถ้าต้องถอน release จริง ให้ boss ลบที่หน้า Releases ของ repo แล้วแจ้ง Lead
